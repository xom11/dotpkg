## Step 2: generating a `pkg.lock` with real commits

No command produces one yet (`update` is Phase 3), so it was generated by a
throwaway PowerShell script — the Phase 3 rehearsal the task asked for,
reproduced below in full. It does exactly what Step 2 specifies: for each of
the 25 declared, installed apps, read the installed version (via the
junction-safe method above) and its bucket (from `install.json`), then walk
`git log --format=%H -- bucket/<app>.json` in that bucket newest-first,
`git show`-ing each commit's blob and comparing its own `version` field,
stopping at the first (= newest) exact match. Filename resolution tries the
declared spelling, then the lowercased spelling, then falls back to a
case-insensitive `git ls-tree` listing at HEAD — mirroring `Scoop::stage`'s
own fallback chain in `src/backend/scoop.rs` exactly, so the rehearsal
exercises the same resolution order Phase 3 will need.

```powershell
function Find-VersionCommit($bucketDir, $pathInRepo, $wantVersion) {
  $commits = & git -C $bucketDir log --format=%H -- $pathInRepo 2>$null
  foreach ($c in $commits) {
    $content = & git -C $bucketDir show "${c}:${pathInRepo}" 2>$null
    if (-not $content) { continue }
    try { $j = ($content -join "`n") | ConvertFrom-Json } catch { continue }
    if ("$($j.version)" -eq $wantVersion) { return $c }
  }
  return $null
}
# ... (filename resolution: "<name>.json", then "<name-lower>.json", then a
#      case-insensitive `git ls-tree --name-only HEAD bucket/` scan)
```

### The wrinkle Step 2 didn't anticipate: an exact-match lock gives `prepare()` nothing to do

Applying this "faithful" `pkg.lock` — the one Step 2 literally asked for —
would produce **zero** `Install`/`Upgrade`/`Downgrade` actions, because
`plan()`'s decision is `Some(cur) if cur.version == want => {}`
(`src/plan.rs`): a locked version identical to the installed version is
treated as nothing to do, silently, by design. That is exactly correct
behaviour for what `update` will normally produce (a lock that matches
reality *should* make `apply` a no-op) — but it also means this lock, run
through `apply --prepare` as-is, cannot exercise manifest recovery, staging,
or download-and-verify at all. There is nothing wrong here; it just means
answering this task's four questions needs a lock that names a version
*other than* what's installed. (This was read from `plan.rs`'s own tested
branch and cross-checked against `tests/planner.rs`'s exact-match coverage,
rather than independently re-run on-machine as a fifth scheduled-task round
trip — see "Not independently exercised" below.)

The same script was therefore extended, after finding the matching commit,
to keep walking the same history backward for one more *distinct* version —
a genuinely older, real commit, not a fabricated one — producing a second
file, `pkg-exercise.lock`. This is scaffolding purpose-built for dogfooding
`prepare()`, not a Phase 3 deliverable, and is presented as such. (The
inherited, interrupted attempt had independently arrived at the identical
technique under the names `t7-current.lock`/`t7-exercise.lock` — further
cross-validation that this is the right way to unblock the test, not an
invented workaround.)

## Step 4: the four questions

### 1. Do all twenty-five declared packages recover their manifests? — Yes, for every case actually exercised

Of 25 declared, 2 (`kanata`, `python`) were genuinely running and correctly
skipped by design before manifest recovery is even attempted — that's a
`Skip`, not a recovery failure. Of the 23 that reached `stage_and_fetch`, all
23 recovered their manifest from the exercise lock's real bucket commits on
the first run; on the corrupted-lock run, the other 22 (everything except the
one deliberately broken entry) recovered theirs too, unaffected by the
neighbor's failure. Separately, the lock-generation script itself resolved a
real commit for all 25 declared apps with no bucket missing and no installed
version absent from history — the fuller claim Step 2 asked about.

### 2. Does every recovered manifest's version match the lock? — Yes, verified directly on disk

Spot-checked three staged manifests after the runs:

```
git\2.55.0.2\git.json        -> version field = 2.55.0.2
beckon\0.2.2\beckon.json     -> version field = 0.2.2
nodejs\26.5.0\nodejs.json    -> version field = 26.5.0
```

Every one matches the lock entry that produced it. This also can't be
otherwise by construction — `stage_text` in `src/backend/scoop.rs` asserts
`got == version` before ever writing a file, covered by the crate's own test
suite — and no run in this session produced a counterexample.

### 3. Do the downloads verify? — Yes, for every attempt that reached the download step

All 24 real download attempts across both runs (23 from the exercise lock +
the one additional `beckon@0.2.2` probe) returned `Outcome::Ready`, which
`stage_and_fetch` only produces after `scoop download` exits 0 — and `scoop
download` hash-verifies by construction (Task 5's own finding: there is no
flag that skips it). Cross-checked independently against the cache: every
file `apply --prepare` reported ready for now exists in
`scoop\cache`, sized plausibly, and nothing reported ready is missing from
it.

### 4. Does a deliberately corrupted lock entry fail loudly and stage nothing? — Yes

- **Loud:** `FAILED  scoop  git   git: commit deadbeef...deadbeef is not in
  bucket "main"` — names the package, the exact bogus commit, and the
  bucket. The overall run's own exit code is **1**, not 0 — `main.rs` calls
  `std::process::exit(1)` whenever `preparation.is_ok()` is false, and a
  `Failed` outcome makes it false. This was checked directly (`exit: 1` in
  the captured runner output), not inferred.
- **Stages nothing for that entry:** the staging tree's `git\` subdirectory
  contains only `2.55.0.2\git.json`, timestamped to the earlier, *valid*
  exercise run — no directory was created for the bogus commit at all (there
  is no version to name one after: `Scoop::stage`'s `git cat-file -e` guard
  rejects the commit before `stage_text` — the only function that writes —
  is ever reached).
- **Isolated:** the other 22 packages in the same run still succeeded (`22
  of 23 changes ready, 1 failed`) — one bad lock entry did not stop, hide, or
  poison its neighbors.

## Step 5: what came back different from the plan's prediction

**The prediction — "some packages will fail because their upstream URL is
gone" — did not come true, and this was tested adversarially rather than
just noted.** After the exercise-lock run's 23/23 succeeded (already reason
for suspicion per the task's own instruction), a targeted probe was run
before concluding anything: `beckon`, the one declared package pinned to a
single-maintainer personal bucket (`xom11/scoop-bucket`, 14 total releases,
the smallest and least-institutional of the three buckets in play), was
pointed at its real second-oldest release (`0.2.2`, never previously
downloaded on this machine) instead of one release back. If any package here
was going to have a deleted GitHub release asset, this was the best
candidate available. **It still succeeded** — `ready scoop beckon 0.2.9 ->
0.2.2 (downgrade)`, and the file landed in the cache
(`beckon#0.2.2#26fd594.zip`, 368,065 bytes). The likely reason: every
manifest in play here points at a GitHub Releases asset, and GitHub does not
garbage-collect release assets on its own — only a maintainer's deliberate
deletion removes one, which is uncommon even for small personal projects at
only a few releases of age. This dogfood therefore did not observe the
failure mode Phase 2b-1 was built to catch; it is recorded as a genuine
negative result; the mechanism (`stage`'s `git cat-file -e` guard,
`stage_text`'s version assertion, `scoop download`'s hash check) was
exercised in full by the deliberately corrupted commit above, which is a
different failure shape (bad git ref, not bad HTTP url) but the closest thing
to upstream rot this session was able to produce evidence for one way or the
other.

Other things worth recording that also didn't match a plan reading literally:

1. **A lock generated to the letter of Step 2 (version == installed) makes
   `apply --prepare` a complete no-op.** Not a bug — `update`'s honest output
   the moment after it runs should be exactly this — but it means the four
   questions can only be answered by deliberately using a different, real,
   older lock, which neither the task brief nor Step 2's instructions state
   outright. Both this session and the independently-authored inherited
   attempt converged on the identical workaround (an "exercise" lock one real
   release back), which is reassuring but also means it's worth writing into
   Phase 3's own design rather than rediscovering per dogfood.
2. **This task had already been substantially attempted and abandoned
   mid-way**, not merely "found unreachable" — see the opening section. The
   standing rule ("report BLOCKED, write nothing" rather than fabricate) held:
   no document existed, even though a working scheduled task and two lock
   files did.
3. The elevated-ssh `current`-junction quirk from Phase 2a (3 of 30 apps
   unreadable through the junction, readable through the resolved `.Target`)
   reproduced identically, on the same 3 apps, in a completely separate
   session. It is a property of the elevated-ssh reconnaissance path, not of
   `dotpkg` itself (the scheduled task runs at medium integrity, where Phase
   2a already measured all 30 apps visible).
4. 7 of 25 apps' current-matching commit was not their bucket's HEAD,
   confirming the lock generator does real history-walking rather than
   trivially grabbing the latest commit every time.
