# dotpkg — design

**Status:** design approved 2026-08-08, not yet implemented.

Declarative package management for Windows. One dotfile declares what should be
installed; a lock file records exactly what was resolved; `dotpkg apply` brings
the machine to that state and says what it is about to do before doing it.

## Why this exists

Windows has no equivalent of `flake.lock` or `brew bundle`. What it has:

| Tool | Declarative? | Version lock | Prune |
|---|---|---|---|
| `scoop export` / `import` | snapshot, not a spec | records version, cannot replay it | no |
| `winget export` / `import` | snapshot | version only, informational | no |
| WinGet Configuration (DSC v3) | **yes**, YAML | **yes**, `version:` property | **no** |
| chocolatey `packages.config` | yes | yes | no |
| chezmoi | files only, not packages | n/a | n/a |

DSC v3 is the closest, and it is genuinely good: idempotent, cross-platform,
`Microsoft.WinGet/Package` takes a `version`. Two gaps keep it from being the
answer here. It has no scoop support, and it has no prune — `_exist: false`
removes a *named* resource, but nothing scans for what is installed and no
longer declared. A file that only ever adds is a snapshot with extra steps.

The community has not filled the gap either. chezmoi is the de-facto standard
for Windows dotfiles and manages *files*; its package story is "run a script".
A representative well-maintained cross-platform chezmoi repo
([patrick-5546/dotfiles](https://github.com/patrick-5546/dotfiles)) documents
its Windows install script and then says: *"I don't use this script anymore, in
favor of WingetUI"* — a GUI. That is where the state of the art actually sits.

## The insight that makes a real lock possible

Scoop buckets are git repositories, and scoop can install from a manifest file
or URL rather than a bucket name:

```
scoop install \path\to\app.json
scoop install \path\to\app.json@version
scoop install <URL>@version
```

A scoop manifest is a pinned URL plus a SHA256 the installer verifies. Measured
on a real machine (a14, Snapdragon X, 2026-08-07):

```
buckets are git clones:  main 78,381 commits · extras 90,105 · xom11 15

git show a28d0c5648:bucket/fzf.json  ->  complete manifest for fzf 0.74.1
  url  = .../v0.74.1/fzf-0.74.1-windows_amd64.zip
  hash = d83a94a68a9203f6366754123c0e4d7a61e16be18a5d845f4838664b330c4f5f
  keys = version, description, homepage, license, architecture, bin,
         checkver, autoupdate
```

`git show` recovers the *whole* historical manifest — `bin`, `depends`,
`installer`, everything — without touching the working tree. So a lock entry
needs only `{bucket, commit, version}` and reproducibility follows, with hash
verification done by scoop itself.

This is why the lock pins a commit rather than vendoring manifest JSON into the
repo: same guarantee, three lines of readable TOML instead of a 1–3 KB JSON
blob per package, and a clean diff when a version moves.

`scoop install app@version` is deliberately **not** used. `scoop help install`
states it "will auto-generate the manifest using current version" — it rewrites
today's manifest with an old version number, which breaks silently when upstream
changes its URL scheme.

## When NOT to use dotpkg

- You want **rollback**. There is no store and no generations. Windows package
  managers are not atomic and dotpkg does not pretend otherwise.
- You want **reproducible winget packages**. winget pins a version, not a hash,
  and only while that version's manifest still exists upstream. Only the scoop
  backend gives a real lock.
- You are on **NixOS, macOS, or Linux**. Use the native answer:
  `environment.systemPackages`, [nix-homebrew](https://github.com/zhaofengli/nix-homebrew),
  or [nix-apt](https://github.com/xom11/nix-apt).
- You want a **single name to work across package managers**. dotpkg is an
  orchestrator, not an abstraction — see "Orchestrator, not abstraction".

## Scope

**v1: scoop and winget.** Both are dogfooded on the author's machine.

**Chocolatey is deferred to v2**, on purpose. It is not installed on the
development machine, so a v1 choco backend would be code that has never run
against a real install — unacceptable for a tool that uninstalls software. It
is also the least valuable of the three: `packages.config` is already a
declarative manifest with versions, so dotpkg would only be adding prune.

The backend trait exists from v1 so choco slots in without touching the planner.

### Orchestrator, not abstraction

Each backend is declared in its own section using its own vocabulary. dotpkg
does not invent a unified package name that maps onto `fzf` (scoop) /
`junegunn.fzf` (winget) / `fzf` (choco).

Maintaining that mapping across three ecosystems is unbounded work and is where
meta-package-managers die. It would also hide the fact that the scoop lock is
strictly stronger than the winget one, which is exactly the thing a user must
not be misled about.

## The three files

Separating intent, resolution, and ownership is the core of the design.

### `pkg.toml` — intent. Hand-written. Committed.

```toml
[scoop]
buckets  = ["main", "extras", "xom11=https://github.com/xom11/scoop-bucket"]
packages = ["fzf", "bat", "ripgrep", "neovim"]

[scoop.opts]
python = { arch = "64bit" }   # force an architecture
kanata = { arch = "keep" }    # never change whatever is installed

[winget]
packages = ["Git.Git", "Brave.Brave", "AutoHotkey.AutoHotkey"]
```

`arch` exists because scoop installs the wrong architecture silently. Scoop's
`default_architecture` is `64bit` until told otherwise, and
`PROCESSOR_ARCHITECTURE` describes the *calling process*, so an emulated x64
shell on an ARM64 machine reports AMD64. That combination left the author's
machine with 17 emulated packages and nothing anywhere saying why.

### `pkg.lock` — resolution. Tool-written. Committed.

Deliberately asymmetric, because the backends are:

```toml
[scoop.fzf]
bucket  = "main"
commit  = "a28d0c5648f1..."
version = "0.74.1"

[winget."Git.Git"]
version = "2.55.0"
pin     = "version-only"
```

`pin` is not decoration. It is where the tool is forbidden from lying about the
guarantee it provides. Flattening the two into one shape would let a user
believe a winget package is as reproducible as a scoop one.

### `state.json` — ownership. Tool-written. **Not** committed.

Lives in `%LOCALAPPDATA%\dotpkg\state.json`:

```json
{ "scoop": { "fzf": "installed", "aichat": "adopted" } }
```

`prune` only ever touches a package named here. Install dotpkg on a machine with
200 existing apps and state is empty, so nothing is removed — but `status` still
reports everything that differs. This is what makes the tool safe to try.

It is not committed because it is the truth of one machine, not shareable
intent — the same reason `flake.lock` is committed and
`/nix/var/nix/profiles` is not.

## Commands

| Command | Effect |
|---|---|
| `dotpkg status` | Print the plan. Change nothing. Reports unadopted packages too. |
| `dotpkg apply` | Print the plan, ask, then execute. `--yes` skips the prompt. |
| `dotpkg update [pkg]` | Re-resolve to latest and rewrite `pkg.lock`. **The only command that writes the lock.** |
| `dotpkg adopt <pkg>` | Bring an already-installed package under management. |
| `dotpkg add <pkg>` | Install, add to `pkg.toml`, record in `pkg.lock`. |

Splitting `update` from `apply` is what makes `apply` deterministic: it never
reaches the network to ask what is newest, so running it today and in six months
produces the same machine.

That split forces two rules which are easy to leave unstated:

- **Declared in `pkg.toml` but absent from `pkg.lock` → `apply` fails** for that
  package, naming it and saying to run `dotpkg update`. It must not resolve the
  latest version itself; that would make `apply` non-deterministic and would
  write the lock from a command that is not allowed to.
- **Present in `pkg.lock` but no longer in `pkg.toml` → prune candidate**,
  subject to the `state.json` fence like any other. `update` drops the entry.

### Plan output

```
$ dotpkg apply
  + scoop  ripgrep     14.1.0          (install)
  ↑ winget Brave.Brave 1.85 → 1.86     (upgrade)
  ↓ scoop  fzf         0.74.2 → 0.74.1 (downgrade, from lock)
  - scoop  aichat      0.30.0          (prune, adopted)
  ! scoop  kanata      running — skipped, stop it first
  ? scoop  antigravity 2.0.6           (unmanaged, not adopted — no action)

  4 changes, 1 skipped. Continue? [y/N]
```

Always showing the plan is what lets the lock stay authoritative without
pretending a downgrade is safe. On Windows a downgrade is uninstall + install,
and the gap between them is where things break; `↓` makes that visible before
it happens rather than after.

`status` is this same code path, printed and exited.

## Architecture

### The planner is pure

```rust
fn plan(
    declared:  &Config,       // pkg.toml
    lock:      &Lock,         // pkg.lock
    installed: &[Installed],  // scanned from backends
    state:     &State,        // who owns what
    running:   &[String],     // process names currently alive
) -> Plan
```

No I/O, no network, no subprocess. Every decision lives here, so the whole
decision layer is testable on Linux and macOS with fabricated inputs.

For a tool that uninstalls other people's software, the decision logic must be
heavily tested, and those tests must not require a Windows machine — a suite
that is expensive to run is a suite that stops being run.

`running` is an **input**, not something the planner discovers. That is what
lets "kanata is running, skipped" appear in `dotpkg status` before anything is
attempted.

### Backends

```rust
trait Backend {
    fn scan(&self) -> Result<Vec<Installed>>;
    fn resolve(&self, pkg: &str) -> Result<Pin>;   // only `update` calls this
    fn install(&self, pkg: &str, pin: &Pin) -> Result<()>;
    fn uninstall(&self, pkg: &str) -> Result<()>;
    fn helpers(&self) -> &[&str];
}
```

`resolve` is the only method that reaches the network, and only `update` calls
it. Everything `apply` needs is already on disk.

### Scanning is asymmetric, and measured

| Backend | Method | Cost (a14, warm) |
|---|---|---|
| scoop | read `apps/*/current/{manifest,install}.json` | **98 ms / 27 apps** |
| winget | `winget list`, cached once per run | **1213 ms** |

For comparison, shelling out to scoop to *ask* questions: `scoop list` 962 ms,
`scoop info <pkg>` 1104 ms, `scoop status` 2767 ms. Per-package `scoop info`
across 25 packages would cost ~27 s against 98 ms of file reads. Subprocesses
are for mutation only.

### `helpers()` and the false-positive problem

Scoop auto-installs extraction helpers (`dark`, `innounp`, `7zip`, `lessmsi`)
and **does not record that it did**. Verified: `install.json` for `dark` is
`{"bucket":"main","architecture":"64bit"}` — byte-identical in shape to `fzf`'s.
No installed manifest declares `depends` either, so there is nothing to infer
from.

So this is a fixed per-backend list. It is small and stable, and it belongs to
the backend rather than the planner.

Its value, measured on a14: 30 installed vs 25 declared gives 5 differences —
`7zip`, `aichat`, `antigravity`, `dark`, `innounp`. Three are helpers. Without
this list the tool reports 5 strays of which 2 are real, a 60% false-positive
rate, which is how a feature gets switched off and never switched back on.

### Recording the lock commit

`update` must record the bucket commit **at resolve time**, not derive it later.
If the bucket has advanced, `git log -1 -- bucket/fzf.json` returns the newest
commit touching that file, not the one that produced the installed version;
recovering it afterwards means walking history comparing `version` fields.

Restore touches no working tree:

```
git -C ~/scoop/buckets/main show <commit>:bucket/fzf.json > %TEMP%\fzf.json
scoop install %TEMP%\fzf.json
```

Hash verification is scoop's own. dotpkg does not reimplement it and must not
pass `--skip-hash-check`.

## Error handling

**Never degrade silently.** If the lock names commit X and the bucket does not
have it, fail — do not install latest instead. A lock that quietly falls back to
"latest" is worse than no lock, because it makes a guarantee that is not there.
Every other rule below is a case of this one.

| Situation | Behaviour | Precedent |
|---|---|---|
| Package's process is running | Skip, show `!` in the plan | Upgrading a keyboard remapper while it holds a low-level hook costs the keyboard on the machine you would need to fix it |
| Uninstall succeeded, install did not restore it | **Hard fail, print the recovery command** | A reinstall once left a machine with no toolchain and nothing on screen explaining it |
| Package absent from `state.json` | Never touched | The prune fence |
| Bucket missing | Offer to clone (URL is in `pkg.toml`) | Same rule as above |
| winget version manifest gone upstream | Report, skip that package | Same rule as above |

**Order: install before uninstall.** If a run dies partway, an extra package is
easier to live with than a missing one.

**Per-package failures accumulate; the run continues** and exits non-zero with a
summary. Stopping halfway through 25 packages leaves a worse state than
finishing the ones that work.

**Downgrades are the one irreducible gap**, because they are uninstall +
install. This cannot be designed away, which is precisely why the plan marks
them `↓` and asks first.

## Testing

| Layer | Runs on | Content |
|---|---|---|
| 1. Planner | any OS, every push | Table-driven: (declared, lock, installed, state, running) → expected plan. The bulk of the suite. |
| 2. Backend scan | any OS, every push | Fabricated scoop directory tree of JSON files; assert `scan()` reads it correctly. |
| 3. Integration | Windows runner, gated | Real scoop in a throwaway `$env:SCOOP`; install, uninstall, and downgrade one small package. |

Layers 1 and 2 needing no Windows is a requirement, not a convenience.

Two tests are mandatory, covering the "this tool ate my machine" scenarios:

1. `prune` refuses to touch a package absent from `state.json`.
2. A lock pointing at a nonexistent commit fails and does **not** install latest.

Both require a **negative control** — break the code deliberately, confirm the
test goes red, restore. An assertion that has never failed has not been shown to
test anything.

## Dogfooding and migration

The author's machine (a14) is the test bed. Its 25 scoop and 17 winget packages
become the first `pkg.toml`, generated by `dotpkg adopt`.

`~/.nix` keeps its existing `apply.ps1`. dotpkg runs alongside it until it is
trusted, and only then replaces the `packages.scoop` and `packages.winget`
modules. The existing PowerShell implementation already handles architecture
drift, running-process guards, and post-uninstall verification; those behaviours
are requirements for dotpkg, not features to be rediscovered.

## Implementation phasing

v1 as specified is more than one sitting: two backends, five commands, three
test layers. It should be built in an order where each step is independently
useful and dogfoodable on a14.

1. **`status`, scoop only.** Config + lock + state types, scoop `scan()`, the
   pure planner, plan rendering. Read-only, so it can run against the real
   machine from day one with nothing at risk.
2. **`apply`, scoop only.** Install and prune, the `state.json` fence, the
   running-process skip, post-uninstall verification.
3. **`update` and `adopt`, scoop.** Bucket commit resolution and the
   `git show` restore path — the reproducibility claim becomes real here.
4. **winget backend.** `scan` via cached `winget list`, version-only pinning.
5. **`add`, polish, docs, release** through the existing scoop bucket.

Steps 1–3 are the whole novel contribution; if the project stalls after 3 it
has still produced something that does not exist today.

## Non-goals

- Rollback or generations.
- A unified cross-manager package namespace.
- Managing dotfiles. chezmoi does that well; dotpkg manages packages.
- Replacing scoop or winget. dotpkg orchestrates them and owns no install logic.
