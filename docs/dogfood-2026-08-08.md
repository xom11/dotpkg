# Dogfood: `dotpkg status` against a real scoop install (a14, 2026-08-08)

Task 9 of the Phase 1 plan. First contact between `dotpkg status` and a real
machine. `status` performs no writes and no subprocess/network calls, so this
run was read-only by construction; the write-safety claim was additionally
verified empirically (see "Read-only, verified" below).

## Build

The brief's Steps 1-2 assume cross-compiling on the Mac with
`--target aarch64-pc-windows-msvc`. That was skipped deliberately — linking to
MSVC from macOS needs the Microsoft linker, which the Mac does not have.
Instead the crate source (`Cargo.toml`, `Cargo.lock`, `src/`, `tests/` —
**not** `target/`, `.git/`, `.superpowers/`) was copied to
`C:\Users\kln\dotpkg-build` on a14 and built natively there:

```
rustc 1.97.1, default host aarch64-pc-windows-msvc
cargo build --release
Finished `release` profile [optimized] target(s) in 45.42s
```

No warnings. `Cargo.lock`'s SHA-256 was identical before and after the build
(`36e2ab70...bdddaa2`), so the native build resolved to exactly the versions
pinned on the Mac — no lockfile drift from building on a different platform.

## The four checks

**1. Is `beckon` found? It comes from the `xom11` bucket, not `main`.**

Not verifiable from the run above by itself — with no lock entry, every
declared package prints the identical `no lock entry` line regardless of
whether the scanner actually found it installed (`plan()` checks
`lock.scoop.get(name)` and bails before ever consulting the scan result). So
this specific check needed a second, still read-only, probe: a lock file
giving `beckon`, `zellij`, `actionlint`, and `git` (a control) a deliberately
wrong low version (`0.0.1`), so a found package prints `downgrade` and a
missed one prints `install`.

```
  v scoop  git            2.55.0.3 -> 0.0.1        (downgrade, from lock)
  v scoop  beckon         0.2.9 -> 0.0.1           (downgrade, from lock)
  + scoop  zellij         0.0.1                    (install)
  + scoop  actionlint     0.0.1                    (install)
```

**Yes, `beckon` is found**, and its version (`0.2.9`) is read correctly. The
bucket does not matter to detection, as expected from reading `plan.rs`.

But the same probe surfaced something the brief didn't anticipate: `zellij`
and `actionlint` — both declared, both genuinely installed
(`~/scoop/apps/zellij/0.44.3`, `~/scoop/apps/actionlint/1.7.12` are real,
non-empty version directories) — come back as `install`, i.e. *not found*.
See the discrepancy section below; it's the same root cause as check 2.

**2. Are exactly `aichat` and `antigravity` reported as unmanaged?**

**No. Only `aichat` is.** `antigravity` does not appear anywhere in the
output — not as `?`, not as anything.

**3. Are all four helpers (`dark`, `innounp`, `7zip`, `lessmsi`) silent?**

**Yes.** `dark`, `innounp`, and `7zip` are installed on this machine and
produce no line; `lessmsi` is not installed at all. All four are confirmed
readable and correctly filtered by `SCOOP_HELPERS` — this is the one check
that came back exactly as the brief expected, and for the reason the brief
expected (name-based filtering), not by accident.

**4. Does any package appear that is not actually in `~/scoop/apps`?**

**No.** Every name in the output is either one of the 25 declared packages or
`aichat`, which is genuinely installed. No fabricated names.

## The discrepancy, and root cause

Check 2's answer is wrong per the brief's expectation, and check 1 needed a
workaround to answer at all. Both trace to the same cause, found by
inspecting the three affected packages directly (`antigravity`, `zellij`,
`actionlint`):

```
> cmd /c dir /a C:\Users\kln\scoop\apps\antigravity
...
07/05/2026  08:46 AM    <JUNCTION>     current [\??\C:\Users\kln\scoop\apps\antigravity\2.0.6]

> [System.IO.File]::ReadAllText("C:\Users\kln\scoop\apps\antigravity\current\manifest.json")
Exception: The path cannot be traversed because it contains an untrusted mount point.
```

Ownership check across all 30 installed apps:

```
actionlint  | owner=ZENBOOK-A14\kln          | manifest_readable=NO
antigravity | owner=ZENBOOK-A14\kln          | manifest_readable=NO
zellij      | owner=ZENBOOK-A14\kln          | manifest_readable=NO
(all other 27 apps)  | owner=BUILTIN\Administrators | manifest_readable=YES
```

This SSH session runs at High Mandatory Level (full admin, no UAC prompt —
already the documented behavior of `ssh a14` for this user). Windows blocks
an elevated/Administrators-context process from traversing an NTFS junction
(scoop's `current` reparse point) whose owner is a different, non-elevated
account — the three affected apps were installed while running as the plain
interactive user, everything else was installed under an elevated scoop
invocation. `Scoop::scan()`'s manifest read
(`src/backend/scoop.rs`) hits exactly this permission error and — by design,
per the comment above it — treats it identically to a half-finished install
and silently skips the entry:

```rust
let Ok(manifest_text) = std::fs::read_to_string(current.join("manifest.json")) else {
    // A half-finished or broken install must not fail the whole scan.
    continue;
};
```

That fallback is correct for its stated purpose. The problem is that it also
catches this unrelated failure mode — a legitimate, fully-installed package
that the *calling process* cannot read because of a security-context
mismatch between the account that ran `scoop install` and the account running
`dotpkg` — and produces the same silent, indistinguishable outcome: the
package vanishes from `status`'s view with no error, no line, nothing. For an
undeclared package (`antigravity`) that means a real piece of unmanaged
software goes unreported. For a declared package under an actual lock file
(not exercised by Task 9's no-lock scenario, but demonstrated by the probe
above) it would misrender as `install` — i.e., in Phase 2, `apply` would try
to reinstall software that is already there.

**Judgement:** the brief's expectation (exactly `aichat` + `antigravity`
unmanaged, and `beckon` found) describes what should happen if `status`'s
scan has full read access to every installed manifest. That is not the
situation on this machine when `status` is invoked over this particular SSH
path. I believe reality is correct and the brief's expectation was formed
without accounting for the account/elevation boundary between how scoop
itself was invoked (mixed — some installs elevated, some not) and how this
dogfood run invoked `dotpkg`. This is not a bug in the four lines of
`scoop.rs` reviewed above; the comment's stated intent (don't fail the whole
scan over one bad entry) is sound. It is a gap in what the silent skip can
mean: a genuinely-missing manifest and a permission-blocked one are
indistinguishable from `status`'s output today. No code was changed for this
task — this is a report, not a fix.

## Timing

The first execution of the freshly built binary took **382 ms**. Five
subsequent warm runs on the same binary, same machine:

```
run 1 : 26.9 ms
run 2 : 20.7 ms
run 3 : 19.2 ms
run 4 : 19.0 ms
run 5 : 19.9 ms
```

Warm-run average ≈ 21 ms, well inside the 98 ms/27-apps benchmark noted in
the task brief (this run scanned 30 installed + 25 declared packages, plus a
full process-table walk via `sysinfo` for the `Running`-skip check). The 18x
gap between the cold and warm runs is consistent with this machine's already
-documented pattern of Windows Defender scanning a binary on its first-ever
execution (see `nvim_windows_cham` project notes) rather than anything in
`dotpkg` itself — no code in the `status` path does anything that would be
slow only once.

## Read-only, verified

- `C:\Users\kln\pkg.lock` (the `--lock` path passed to every run): absent
  before, absent after, every run.
- `%LOCALAPPDATA%\dotpkg\state.json`: absent before, absent after.
- `Cargo.lock`'s SHA-256 was identical before and after the native build (no
  drift from resolving on a different platform).
- Everything `status` reads sits under `~/scoop/apps` and was opened, never
  written; `src/main.rs`'s `Status` handler and everything it calls
  (`config::load`, `lock::load_or_empty`, `State::load_or_empty`,
  `Scoop::scan`, `sys::running_process_names`, `plan::plan`, `render::render`)
  contain no write, no subprocess spawn, and no network call.
- The one write that happened on the machine during this task —
  `C:\Users\kln\pkg-probe.lock`, the supplementary lock file used to answer
  check 1 — was authored by the investigator as test input, not by `dotpkg`,
  and was deleted again before finishing.
